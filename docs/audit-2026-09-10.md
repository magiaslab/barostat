## 1. `crypto.randomUUID()` non esiste fuori da un contesto sicuro — ALTO

`src/lib/local/dexie.ts:46`

`crypto.randomUUID` è disponibile solo in contesto sicuro: `https`, `localhost`, `file`. Quando aprirai il dev server dal tablet all'indirizzo di rete — `http://192.168.x.x:3000`, cioè esattamente il modo in cui proverai il layout primario — **la funzione è `undefined` e ogni tap solleva un errore**. In locale sul Mac non se ne accorge nessuno.

Correzione: un fallback esplicito.

```ts
function newId(): string {
  if (typeof crypto !== "undefined" && "randomUUID" in crypto) return crypto.randomUUID();
  const b = crypto.getRandomValues(new Uint8Array(16));
  b[6] = (b[6] & 0x0f) | 0x40;
  b[8] = (b[8] & 0x3f) | 0x80;
  const h = [...b].map((x) => x.toString(16).padStart(2, "0"));
  return `${h.slice(0,4).join("")}-${h.slice(4,6).join("")}-${h.slice(6,8).join("")}-${h.slice(8,10).join("")}-${h.slice(10).join("")}`;
}
```

In alternativa `next dev --experimental-https`, ma il fallback serve comunque: il service worker della fase 9 richiede anch'esso contesto sicuro.

## 9. L'indice `syncedAt` è cieco proprio sulle righe che dovrebbe trovare — ALTO

Verificato: con una riga in coda e una sincronizzata,

```
.where("syncedAt").equals(null)          → TypeError: Invalid key provided.
.where("syncedAt").belowOrEqual(maxKey)  → 1 riga su 2, e mostra solo quella GIÀ sincronizzata
```

Oggi non fa danni perché `listPendingEvents` filtra in JavaScript. Il pericolo è che l'indice esiste e sembra utilizzabile: alla fase 8 la cosa più naturale da scrivere è `.where("syncedAt")`, e quella query o solleva un'eccezione o restituisce l'esatto complemento di ciò che serve — cioè invia di nuovo il già inviato e non invia mai il resto.

Correzione: **rimuovere `syncedAt` dagli indici** e lasciare un commento che spieghi perché non va rimesso. Con ~70 eventi a partita il filtro in JavaScript è la scelta giusta. Se un giorno servisse davvero un indice, la strada è un campo separato `pending: 0 | 1`, che è indicizzabile.

## 10. Un annulla durante l'invio fa sparire la cancellazione — ALTO

`src/lib/local/dexie.ts:71`

`markSynced` marca per id, senza verificare che la riga sia ancora quella spedita. Sequenza reale in palestra, con un hotspot lento:

1. la coda spedisce l'evento A, ancora vivo;
2. mentre la richiesta è in volo, l'allenatore annulla A → diventa tombstone, `syncedAt` torna a `null`, rientra in coda;
3. arriva la risposta, `markSynced([A])` scrive `syncedAt = now` **sul tombstone**.

Verificato: dopo il `markSynced` la coda è vuota, la riga è un tombstone, ed è marcata come inviata. La cancellazione non partirà mai. Sul tablet il canestro è annullato, su Neon resta: le due verità divergono in silenzio, che è esattamente ciò che il punto 2 voleva evitare.

Correzione: marcare per **identità più stato**, non per solo id.

```ts
export async function markSynced(
  entries: { id: string; deletedAt: number | null }[],
): Promise<void> {
  const store = getDb();
  const now = Date.now();
  await store.transaction("rw", store.events, async () => {
    for (const entry of entries) {
      const event = await store.events.get(entry.id);
      // Se nel frattempo l'evento è cambiato, resta in coda: quel cambiamento
      // non è ancora stato spedito.
      if (!event || event.deletedAt !== entry.deletedAt) continue;
      await store.events.put({ ...event, syncedAt: now });
    }
  });
}
```

Test da aggiungere: annullare un evento fra `listPendingEvents` e `markSynced` deve lasciarlo in coda.

## 12. Il download è l'unico percorso mai provato sul device vero — ALTO

`src/lib/export/excel.ts:43`, `src/lib/export/pdf.ts:99`

`XLSX.writeFile` e `doc.save()` fanno la stessa cosa: creano un blob e simulano il clic su un link con `download`. Nel browser desktop funziona — ed è lì che è stata fatta la prova.

Il problema è dove l'app verrà davvero usata: **su iPad, installata sulla schermata Home**, cioè in modalità standalone. Lì il download da blob è storicamente inaffidabile su iOS, con comportamenti diversi da una versione all'altra: a volte apre una scheda vuota, a volte non fa nulla. E l'installazione sulla schermata Home non è opzionale — serve a impedire che Safari cancelli lo storage fra una partita e l'altra. Le due cose si scontrano.

C'è una via che risolve il problema e migliora anche il flusso: **la Web Share API con file**.

```ts
async function deliver(blob: Blob, filename: string, mime: string) {
  const file = new File([blob], filename, { type: mime });
  if (navigator.canShare?.({ files: [file] })) {
    await navigator.share({ files: [file], title: filename });
    return "shared";
  }
  const url = URL.createObjectURL(blob);          // fallback desktop
  const a = document.createElement("a");
  a.href = url; a.download = filename; a.click();
  setTimeout(() => URL.revokeObjectURL(url), 1000);
  return "downloaded";
}
```

Su iPad apre il foglio di condivisione: da lì il file va direttamente in WhatsApp allo staff o in Mail, che è esattamente ciò che serve la sera della partita — meglio di un file depositato in Файл. Su desktop resta il download di adesso.

Richiede di passare da `XLSX.writeFile(wb, name)` a `XLSX.write(wb, { type: "array", bookType: "xlsx" })` e da `doc.save(name)` a `doc.output("blob")`, poi entrambi a `deliver`.

**Da provare sull'iPad, in standalone, prima di considerare chiusa la fase 6.** È l'unica parte dell'app che nessun test può coprire.

## 16. Il service worker mette in cache l'HTML delle pagine protette — MEDIO

`public/sw.js`, `SHELL_URLS` e il `cache.put` del gestore `fetch`

`/games` e `/login` vengono precaricati all'installazione e ricacheati a ogni visita. Ma ora sono pagine dietro autenticazione: `fetch` segue i redirect, quindi se la sessione manca la risposta finale è l'HTML del login **salvato sotto la chiave `/games`**. Da lì in poi, offline, `/games` serve la schermata di accesso — e offline non c'è modo di superarla. È lo scenario peggiore: succede in palestra, senza rete, con la partita che sta per cominciare.

Correzione: non mettere in cache le navigazioni HTML (`request.mode === "navigate"`), o almeno non memorizzare risposte con `response.redirected === true`, e togliere `/games` e `/login` da `SHELL_URLS`. Gli asset sotto `/_next/static` restano in cache a runtime e sono quelli che servono davvero per aprire l'app offline.

## 17. Offline l'app non si apre più — ALTO

`public/sw.js`

Messi insieme, i due gestori non memorizzano **nessun HTML**:

- `SHELL_URLS` contiene solo manifest e icone. L'unica pagina rimasta, `/`, è un `redirect("/games")`: la Cache API rifiuta di memorizzare una risposta con `redirected === true`, e l'errore viene inghiottito da `.catch(() => undefined)`. Quindi `/` non entra in cache.
- Il gestore `fetch` mette in cache solo se `request.mode !== "navigate"`: le pagine non vengono mai memorizzate.

Di conseguenza, offline: `caches.match(request)` non trova nulla, si passa al ripiego per le navigazioni, `caches.match("/games")` restituisce `undefined`, e `respondWith(undefined)` diventa un errore di rete. **Aprendo l'app dalla schermata Home senza rete si vede la pagina di errore del browser.**

È lo scenario del collaudo — modalità aereo, riapri l'app — ed è il requisito centrale del progetto.

## La correzione

La condizione giusta non è «non memorizzare le navigazioni», è «non memorizzare una risposta che non sia una pagina vera». Un redirect al login ha `redirected === true` e viene escluso da solo; la pagina autenticata, una volta caricata online, resta e serve per l'avvio offline.

```js
.then((response) => {
  // Anche le navigazioni: ma solo pagine vere. Un redirect al login ha
  // redirected === true e resta fuori, così non finisce sotto /games.
  if (response.ok && !response.redirected && response.type === "basic") {
    const copy = response.clone();
    void caches.open(SHELL).then((cache) => cache.put(request, copy));
  }
  return response;
})
```

Il ripiego `caches.match("/games")` per le navigazioni resta com'è: dopo la prima apertura online la voce esiste. Togliere `/` da `SHELL_URLS`, che è un redirect e non entrerà mai in cache. Portare `SHELL` a `v3` per ripartire pulito.

Collaudo, in quest'ordine: apri l'app online e vai su `/games`; modalità aereo; chiudi e riapri dalla schermata Home. Deve aprirsi e far segnare.

## 18. `getDeviceId` viene chiamata durante il render — BASSO

`src/components/live/live-screen.tsx`

Il passaggio a `useSyncExternalStore` toglie il `setState` nell'effect, ed è giusto. Ma `getSnapshot` è `getDeviceId`, che se l'id non esiste lo crea e lo scrive in `localStorage`: una scrittura durante il render. Funziona perché è idempotente, e la regola di React che vieta gli effetti nel render esiste proprio per i casi in cui non lo è.
