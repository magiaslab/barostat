## 1. `crypto.randomUUID()` non esiste fuori da un contesto sicuro — ALTO

`src/lib/local/dexie.ts:46`

`crypto.randomUUID` è disponibile solo in contesto sicuro: `https`, `localhost`, `file`. Quando aprirai il dev server dal tablet all'indirizzo di rete — `http://192.168.x.x:3000`, cioè esattamente il modo in cui proverai il layout primario — **la funzione è `undefined` e ogni tap solleva un errore**. In locale sul Mac non se ne accorge nessuno.

Correzione: un fallback esplicito.

```ts
function newId(): string {
  if (typeof crypto !== "undefined" && "randomUUID" in crypto) return crypto.randomUUID();
  const b = crypto.getRandomValues(new Uint8Array(16));
  b[6] = (b[6] & 0x0f) | 0x40;
  b[8] = (b[8] & 0x3f) | 0x80;
  const h = [...b].map((x) => x.toString(16).padStart(2, "0"));
  return `${h.slice(0,4).join("")}-${h.slice(4,6).join("")}-${h.slice(6,8).join("")}-${h.slice(8,10).join("")}-${h.slice(10).join("")}`;
}
```

In alternativa `next dev --experimental-https`, ma il fallback serve comunque: il service worker della fase 9 richiede anch'esso contesto sicuro.

## 2. Le cancellazioni non potranno mai essere sincronizzate — ALTO

`src/lib/local/dexie.ts:38`, `src/lib/types.ts:6`

`undoLast` scrive un tombstone (`deletedAt`), ma `listLiveEvents` lo filtra via e **nessuna funzione espone gli eventi cancellati**. Inoltre `GameEvent` non ha un campo che distingua ciò che è già stato inviato da ciò che è in coda.

Conseguenza alla fase 8: un evento annullato *dopo* essere stato sincronizzato resterà su Neon per sempre, e il riepilogo sul server divergerà da quello sul tablet. Non è un bug oggi, ma il modello dati è appena stato scritto ed è il momento giusto per chiuderlo:

- aggiungere `syncedAt: number | null` a `GameEvent`;
- aggiungere `listPendingEvents(gameId)` che restituisce **anche** i tombstone non ancora inviati;
- l'indice diventa `id, gameId, [gameId+seq], syncedAt`.

## 4. Finestra in cui il punteggio può apparire azzerato — MEDIO

`src/lib/local/use-game-events.ts:58`

`snapshot` parte a `null` e si popola al primo emit di `liveQuery`. Se un tap arriva **prima** di quel primo emit, l'aggiornamento ottimistico parte da `EMPTY_EVENTS` e produce uno snapshot con un solo evento, con `ready` che diventa `true`. Per qualche millisecondo la schermata mostra il tabellone azzerato, poi `liveQuery` corregge.

Rarissimo, ma succede proprio nel caso peggiore: riapri una partita in corso e tocchi subito. Vedere 0–0 a metà terzo quarto è il genere di cosa che fa perdere fiducia nell'app. Due rimedi, entrambi validi: non applicare l'ottimistico quando `prev` è `null`, oppure disabilitare la griglia finché `ready` è falso.

## 5. `stats.ts` scandisce gli eventi molte volte più del necessario — MEDIO

`teamStats` chiama `gridCounts`, poi `pointsByBand` (che richiama `gridCounts`) e `freeThrows` (che lo richiama ancora): tre scansioni dove ne basta una. `cellCount` calcola l'**intera** griglia per leggere una cella: se la fase 4 disegnasse le 24 celle con `cellCount`, sarebbero 24 scansioni complete a ogni render, cioè a ogni tap.

Con 80 eventi restano poche migliaia di iterazioni: **non è un problema di prestazioni oggi**. È un problema di struttura, che diventa reale il giorno del confronto stagionale su venti partite. Da sistemare ora che costa dieci minuti: una sola `gridCounts` e tutto il resto derivato da quella.

## 9. L'indice `syncedAt` è cieco proprio sulle righe che dovrebbe trovare — ALTO

`src/lib/local/dexie.ts:41`

IndexedDB non sa indicizzare `null`: le chiavi ammesse sono stringhe, numeri, date e array. Le righe con `syncedAt: null` — cioè **tutte e sole quelle in coda** — non entrano nell'indice.

Verificato: con una riga in coda e una sincronizzata,

```
.where("syncedAt").equals(null)          → TypeError: Invalid key provided.
.where("syncedAt").belowOrEqual(maxKey)  → 1 riga su 2, e mostra solo quella GIÀ sincronizzata
```

Oggi non fa danni perché `listPendingEvents` filtra in JavaScript. Il pericolo è che l'indice esiste e sembra utilizzabile: alla fase 8 la cosa più naturale da scrivere è `.where("syncedAt")`, e quella query o solleva un'eccezione o restituisce l'esatto complemento di ciò che serve — cioè invia di nuovo il già inviato e non invia mai il resto.

Correzione: **rimuovere `syncedAt` dagli indici** e lasciare un commento che spieghi perché non va rimesso. Con ~70 eventi a partita il filtro in JavaScript è la scelta giusta. Se un giorno servisse davvero un indice, la strada è un campo separato `pending: 0 | 1`, che è indicizzabile.

## 10. Un annulla durante l'invio fa sparire la cancellazione — ALTO

`src/lib/local/dexie.ts:71`

`markSynced` marca per id, senza verificare che la riga sia ancora quella spedita. Sequenza reale in palestra, con un hotspot lento:

1. la coda spedisce l'evento A, ancora vivo;
2. mentre la richiesta è in volo, l'allenatore annulla A → diventa tombstone, `syncedAt` torna a `null`, rientra in coda;
3. arriva la risposta, `markSynced([A])` scrive `syncedAt = now` **sul tombstone**.

Verificato: dopo il `markSynced` la coda è vuota, la riga è un tombstone, ed è marcata come inviata. La cancellazione non partirà mai. Sul tablet il canestro è annullato, su Neon resta: le due verità divergono in silenzio, che è esattamente ciò che il punto 2 voleva evitare.

Correzione: marcare per **identità più stato**, non per solo id.

```ts
export async function markSynced(
  entries: { id: string; deletedAt: number | null }[],
): Promise<void> {
  const store = getDb();
  const now = Date.now();
  await store.transaction("rw", store.events, async () => {
    for (const entry of entries) {
      const event = await store.events.get(entry.id);
      // Se nel frattempo l'evento è cambiato, resta in coda: quel cambiamento
      // non è ancora stato spedito.
      if (!event || event.deletedAt !== entry.deletedAt) continue;
      await store.events.put({ ...event, syncedAt: now });
    }
  });
}
```

Test da aggiungere: annullare un evento fra `listPendingEvents` e `markSynced` deve lasciarlo in coda.
